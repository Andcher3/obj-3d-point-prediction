# E3 严格身份审计结果复核

- 日期：2026-09-24
- 状态：监督登记仍未通过；不启动 Relation Head 训练

## 结果判断

- 五个视频均为 `48/48` 有效 query，2D anchor 和 2D `k=3` 图均通过；3D 登记 gate 全部失败。
- 留出 3D 登记 `p90` 为 `34.52%`、`26.23%`、`20.84%`、`7.40%`、`30.18%`；最大误差为 `59.15%`、`47.77%`、`49.32%`、`39.39%`、`51.50%`。
- `9069...` 的主体 query 相对稳定，但仍有 2 个 query 超过 10%、最大误差接近 40%，不能放行正式监督。
- 直接 UV 采样后的相似拟合 p90 在五个视频为 `0.088--0.339 m`，跨点距离误差也普遍较大，支持跨 DA3 上下文几何不一致的判断。
- 当前证据足以维持训练阻塞，但不能把全部误差归因于 TrackCraft3R 的 query identity。两次运行按相同 query UV 独立选点，误差也可能来自 DA3 跨上下文的深度、尺度和局部几何差异。

## 必须补充的诊断

- 让每个 cross-fitting fold 同时输出训练点拟合残差和留出点残差，区分整体坐标不一致与 query 错配。
- 使用真实目标 `bbox_xyxy` 计算 2D 归一化尺度；正式审计已输出真实 bbox，但主严格审计 JSON 仍保留 query-cloud 尺度字段，最终报告应明确采用的尺度。
- 修正辅助诊断字段：`surface_relation_e3_strict_diagnostics.py` 中的 `query_nearest_neighbor_px` 和 `query_second_neighbor_gap_px` 实际来自 query 点之间的 `cKDTree` 间距，并非 query 到 dense track 候选的匹配距离与候选间隔。修正前不能用它们解释近邻 track 误选。
- 实际计算 2D 图的 bridge 边；当前严格审计 JSON 中 `bridge_edges` 仍为空占位。
- 加入同一 dense 运行的自一致性对照、直接相同 UV/双线性采样对照，以及预注册的多组空间平衡 query 划分，排除审计实现和单一四折划分造成的假失败。
- 三个剩余视频已完成，五个视频均未通过监督登记 gate；在诊断修正前不得训练，也不得放宽阈值。

## 后续决策分支

- 若同一运行自一致、不同上下文仍失败：监督问题是跨 DA3 上下文坐标不一致，应改为在单一坐标链中构造未来 pseudo-GT，或改用不依赖绝对 3D 对齐的关系目标。
- 若直接 UV/平衡划分显著改善：先修正 query 对应和审计实现，再重做五视频闸门。
- 即使部分视频通过，也只能作为 E3-lite 诊断样本；当前五视频不能支持正式 Relation Head 泛化结论。

## 当前决定

- 不再继续尝试不同历史窗口长度来放行当前跨上下文绝对 3D pseudo-GT。
- 可以保留现有输出作为失败审计证据，并开展一次小规模单一上下文或关系不变目标的可行性检查；检查完成前不训练 Relation Head。
- E3-lite 只允许使用合成、oracle 或 E1 受控目标验证梯度与接口，不得把结果解释为真实视频监督效果。
